# Предложение: импорт каталогов поставщиков

## Зачем

HTTP-запрос каталога уже возвращает канонические данные об отелях, но в проекте пока нет процесса загрузки данных поставщиков. В задании Trivio описаны два заметно разных источника: большой файл NDJSON и ежедневный XML-файл, в котором весь документ находится в одной строке.

Для каждого поставщика нужно настраивать включение импорта, интервал проверки источника, размер дочерней задачи и минимальный процент успешных дочерних задач (по умолчанию 80%). Импорт отслеживается родительской задачей и дочерними задачами chunks; воркер переводит задачу в `in_progress`, после пяти повторов сверх первой попытки задача переходит в `error`. Способ доставки задач ещё выбирается: рассматривается Laravel Queue на MySQL или собственные воркеры над таблицами задач. Для зависших задач задан порог отсутствия heartbeat более пяти минут; механизм его реализации зависит от выбора очереди.

## Предлагаемый объём

- Определить границу импорта файлов поставщиков и добавить небольшие синтетические примеры обоих форматов.
- Настраивать расписание проверок и параметры обработки отдельно для каждого поставщика.
- Отслеживать импорт и его дочернюю работу: поставщик, контрольную сумму или версию источника, статус, число записей и ошибки.
- Читать файлы потоком и проверять записи отелей и типов номеров.
- Хранить идентификаторы и исходные данные поставщика отдельно от канонического каталога, чтобы следующий этап Matching мог связывать их.
- Сделать повторную обработку chunks безопасной; отдельно определить, когда импорт считается достаточно полным, чтобы искать записи, отсутствующие в новом файле, и что с ними делать.
- Оставить получение файлов по SFTP/API, production-планировщик, сопоставление и обновление поискового индекса за пределами первого этапа.

## Что не входит

- Проверка доступности, получение актуальной цены через API поставщика 1 и бронирование.
- Использование RabbitMQ как очереди для chunks импорта.
- Алгоритм сопоставления отелей и интерфейс ручной проверки.
- Production object storage, учётные данные SFTP, клиенты API поставщиков и production-воркеры.
- Заявления о производительности на миллионах записей на основании маленьких примеров.

## Предлагаемый первый вертикальный сценарий

Первый технический участок — миграции и persistence/domain models, как описано в `design.md`; он не обрабатывает файлы. После ревью этого участка следующий вертикальный сценарий использует локальный файл, MySQL и выбранный транспорт задач, затем добавляет readers обоих форматов. XML читается потоком: однострочный документ нельзя делить по границам строк, как NDJSON.

До миграций нужно одобрить ER-схему и решить блокирующие вопросы из design.md. До полного вертикального сценария отдельно согласуются транспорт задач, механизм heartbeat/lease, XML chunking и критерий полноты импорта.
