# Спецификация импорта файлов поставщиков

## Требование: настраивать автоматическую проверку источников

Система ДОЛЖНА хранить настройки импорта отдельно для каждого поставщика.

### Сценарий: настроить импорт поставщика

КОГДА для поставщика сохраняются настройки импорта
ТОГДА можно указать, включён ли импорт
И интервал проверки появления нового файла
И размер дочерней задачи в записях источника
И минимальную долю успешно завершённых дочерних задач
И если порог успешности не задан, используется значение 80 процентов.

## Требование: планировать проверки по настройкам в базе

Система ДОЛЖНА запускать проверку поставщиков по интервалам из базы данных, не требуя отдельного cron-расписания для каждого поставщика.

### Сценарий: проверить источник по расписанию

ДАНО, что для поставщика включён импорт и наступил срок проверки источника
КОГДА запускается плановая проверка
ТОГДА система проверяет, доступен ли новый файл или версия каталога
И создаёт не более одной родительской задачи для версии этого файла.

ДАНО, что импорт поставщика выключен или срок следующей проверки ещё не наступил
КОГДА запускается плановая проверка
ТОГДА новая родительская задача не создаётся.

ДАНО, что для поставщика ещё не заведена строка настроек импорта
КОГДА запускается плановая проверка
ТОГДА новая родительская задача не создаётся.

## Требование: отслеживать родительские и дочерние задачи

Система ДОЛЖНА представлять импорт версии файла родительской задачей и делить его обработку на дочерние задачи.

### Сценарий: подготовить дочерние задачи

ДАНО, что создана родительская задача для новой версии файла
КОГДА родительский обработчик подготавливает импорт
ТОГДА он создаёт дочерние задачи согласно размеру из настроек поставщика
И сохраняет достаточно данных, чтобы диагностировать результат каждой задачи.

### Сценарий: захватить задачу для обработки

ДАНО, что задача ожидает обработки или доступна для повтора
КОГДА воркер начинает её обработку
ТОГДА статус задачи меняется на `in_progress`
И задача не должна одновременно считаться захваченной несколькими воркерами.

## Требование: восстанавливать зависшие задачи и ограничивать повторы

Система ДОЛЖНА восстанавливать задачу, если heartbeat её обработки не обновлялся более пяти минут.

### Сценарий: истёк heartbeat задачи

ДАНО, что задача находится в `in_progress`
И её heartbeat не обновлялся более пяти минут
КОГДА система обнаруживает истёкшее владение задачей
ТОГДА задачу можно повторно обработать
И прежний воркер не может зафиксировать результат после потери владения.

### Сценарий: исчерпан лимит повторов

ДАНО, что обработка задачи завершилась ошибкой
И исчерпаны пять повторов после первой попытки
КОГДА задача завершается окончательной ошибкой
ТОГДА её статус становится `error`.

## Требование: безопасно повторять обработку chunks

Система ДОЛЖНА выдерживать повторное выполнение дочерней задачи.

### Сценарий: задача повторена после частичной обработки

ДАНО, что воркер частично обработал chunk, а затем потерял владение задачей
КОГДА другой воркер повторно обрабатывает этот chunk
ТОГДА повторные исходные записи не создают дубликаты данных поставщика
И задача получает конечный результат либо завершается статусом `error` после лимита повторов.

## Требование: оценивать результат родительской задачи по доле успеха

Система ДОЛЖНА сравнивать долю успешных дочерних задач с минимальным порогом из настроек поставщика.

### Сценарий: импорт достиг минимального порога

ДАНО, что все дочерние задачи родительского импорта завершены
И доля задач со статусом `done` не ниже настроенного порога
КОГДА оценивается результат импорта
ТОГДА родительская задача получает статус `done`.

### Сценарий: импорт не достиг минимального порога

ДАНО, что все дочерние задачи родительского импорта завершены
И доля задач со статусом `done` ниже настроенного порога
КОГДА оценивается результат импорта
ТОГДА родительская задача получает статус `error`.

## Требование: читать большие файлы постепенно

Система ДОЛЖНА обрабатывать каталоги, не загружая весь файл в память приложения.

### Сценарий: чтение NDJSON

ДАНО, что файл содержит одну запись отеля на строку
КОГДА reader обрабатывает файл
ТОГДА каждая строка обрабатывается как отдельная запись
И работа делится только между целыми записями.

### Сценарий: чтение однострочного XML

ДАНО, что файл содержит много отелей в одном XML-документе на одной физической строке
КОГДА reader обрабатывает файл
ТОГДА он использует потоковый разбор
И не считает границы строк границами записей.

## Требование: не считать отсутствующие записи по неполному импорту

Импорт обновляет текущие строки поставщика по стабильному внешнему идентификатору и записывает ID родительского импорта в `last_seen_import_id`. Система НЕ ДОЛЖНА считать отсутствующими записи по импорту, который не прошёл согласованный критерий полноты.

### Открытый вопрос: обработка отсутствующих записей

Требует согласования, достаточно ли порога успешности 80%, чтобы определить отсутствующие записи, если часть дочерних задач завершилась ошибкой, и что делать с такими записями (например, оставить без изменения или пометить неактивными).

## Требование: изолировать форматы поставщиков

Система ДОЛЖНА держать правила чтения NDJSON/XML и преобразования исходных полей на границе интеграции с соответствующим поставщиком.

### Сценарий: изменился формат одного поставщика

КОГДА поставщик добавляет или меняет поля в своём файле
ТОГДА изменение обрабатывается в reader или слое преобразования этого поставщика
И в readers других поставщиков и канонический контракт Catalog не добавляются условия, специфичные для изменённого источника.
