## Архитектурная основа

Используй облегчённый модульный монолит:

- организация верхнего уровня — package by feature / bounded context;
- внутри бизнес-модуля — `Domain`, `Application`, `Infrastructure`, `UI` по мере реальной необходимости;
- DDD — для областей с бизнес-инвариантами;
- CQRS-lite — отдельные Commands и Queries без обязательных отдельных БД;
- Hexagonal Architecture — на реальных внешних границах;
- один deployment, пока нет доказанной причины выделять сервис.

Предварительные кандидаты в модули: `Catalog`, `SupplierIntegration`, `Availability`, `Booking`, `Import`, `Matching`, `Search`. Это гипотеза, а не обязательная структура. Проверяй границы на use cases и жизненных циклах данных.

### Направление зависимостей

```text
UI ─────────────► Application ─────────────► Domain
Infrastructure ────────────────────────────► Domain/Application ports
```

Domain не должен зависеть от Laravel HTTP, Eloquent, facades, Redis, RabbitMQ, Elasticsearch или HTTP-клиентов поставщиков.

Модуль не обращается к внутренним классам другого модуля. Межмодульное взаимодействие идёт через публичный контракт или integration event.

Не создавай все каталоги заранее. Каталог и абстракция появляются вместе с первым реальным классом и решаемой проблемой.

## DDD

Используй богатую доменную модель там, где есть инварианты и переходы состояния. В первую очередь это `Booking`: идемпотентность, snapshot условий, допустимые статусы, попытки поставщика и неопределённый результат после timeout.

Каталог и поисковые проекции преимущественно data-oriented. Не создавай Value Object, фабрику, интерфейс или агрегат для каждой таблицы и колонки.

Бизнесовое изменение выражай методом модели (`confirm`, `reject`, `markUnknown`), а не произвольной записью значения status извне.

## CQRS-lite

- Command выражает намерение изменить состояние и имеет одного handler.
- Query не изменяет состояние и возвращает read DTO/view model.
- Domain Event описывает уже произошедший бизнес-факт и может иметь несколько обработчиков.
- Query side может использовать Eloquent Builder, Query Builder, SQL, Redis или Elasticsearch напрямую через специализированный query service/port.
- Отдельные физические хранилища, eventual consistency и message bus не являются обязательным следствием CQRS.

Контроллеры должны быть тонкими: HTTP mapping, вызов use case, формирование ответа. Не помещай в контроллеры бизнес-правила или сложные запросы.

## Eloquent и репозитории

Не создавай generic/base repository и CRUD-репозиторий для каждой Eloquent-модели.

- Для `Catalog`, служебных данных импорта и read side допустимо использовать Eloquent/Query Builder внутри Application Query Handler или специализированного query service.
- Для бизнес-критичного агрегата `Booking` сохраняй Repository Port. Доменный агрегат не обязан быть Eloquent-моделью; инфраструктурный репозиторий может маппить его на persistence records.
- Repository используется для загрузки и сохранения агрегата, а не потому, что существует таблица.
- Массовый импорт выполняй через специализированный bulk writer и chunk/bulk operations, а не поштучный `Model::save()`.
- Поиск оформляй как query port (например, `HotelSearch`) с заменяемыми MySQL и Elasticsearch adapters.

## Порты и адаптеры

Выделяй интерфейсы на реальных внешних границах:

- API и каталоги поставщиков;
- часы и генерация идентификаторов, если это требуется тестами;
- persistence агрегатов;
- поисковый движок;
- брокер сообщений и outbox publisher;
- файловое/object storage.

Не оборачивай каждый Laravel-компонент собственным интерфейсом без практической причины.

Поставщики реализуют общий прикладной контракт, но их capabilities могут различаться. Не размазывай проверки конкретного поставщика по handlers и контроллерам.

## Events, queues и надёжность

Различай:

- Domain Event — бизнес-факт внутри доменной модели;
- Integration Event — версионированный публичный контракт между модулями/системами;
- Change Event / audit — техническое изменение данных.

Laravel Event и Laravel Job являются инфраструктурными механизмами и не становятся Domain Command/Event автоматически.

Асинхронные handlers проектируй под at-least-once delivery и делай идемпотентными. Для бронирования не выполняй слепой retry после timeout поставщика: результат может быть `UNKNOWN` и требовать reconciliation.

Transactional Outbox добавляй для решения dual-write между MySQL и брокером. Запись агрегата и outbox event выполняются в одной DB-транзакции; публикация происходит отдельным процессом.

## Laravel-правила

- Используй constructor injection и явные container bindings на неоднозначных границах.
- Для HTTP validation используй Form Requests или типизированное преобразование на границе.
- Публичный JSON формируй через API Resources/read DTO, не сериализуй ORM-модель бесконтрольно.
- Транзакционная граница принадлежит Application use case, а не контроллеру.
- Не передавай Eloquent-модели с загруженным графом отношений в очередь без необходимости; предпочитай идентификаторы и повторную контролируемую загрузку.
- Любой внешний вызов должен иметь определённые timeout, retry policy и обработку ошибок.
- Персональные данные гостей не должны попадать в обычные логи и payload сообщений без необходимости.

## Тестирование

Проверяй поведение на подходящем уровне:

- Domain unit tests — инварианты и переходы состояний;
- Application tests — handlers с fake/in-memory adapters;
- Infrastructure integration tests — Eloquent mapping, SQL constraints, Redis, RabbitMQ, Elasticsearch и реальные adapters;
- HTTP feature tests — полный API-контракт;
- contract tests — одинаковое поведение адаптеров поставщиков.

Тесты должны покрывать негативные, конкурентные и повторные сценарии: duplicate request, repeated message, timeout, stale offer, partial supplier failure и повторный импорт.

## Spec-Driven Development и ADR

Для нетривиального изменения сначала подготовь change-пакет в `openspec/changes/<change-name>/`:

- `proposal.md` — зачем изменение нужно, его scope и non-goals;
- `specs/<capability>/spec.md` — наблюдаемое поведение и проверяемые сценарии;
- `design.md` — технический способ реализации, границы и компромиссы;
- `tasks.md` — проверяемый план реализации.

Не начинай реализацию, пока пользователь не одобрил поведение и значимые компромиссы. После реализации проверь соответствие кода, тестов, design и specification. Завершённое изменение архивируется, а актуальное поведение переносится в `openspec/specs/`.

Полный change-пакет не нужен для механического или очевидного локального изменения. Масштаб документации должен соответствовать риску и числу затронутых границ.

Архитектурно значимые решения фиксируй в `docs/adr/`. ADR отвечает на вопрос «почему выбран этот вариант», а specification — «как система должна себя вести». Создавай ADR, когда решение долгоживущее, влияет на несколько изменений, имеет реальные альтернативы или дорого отменяется. Не создавай ADR для имён классов и обычных деталей реализации.

ADR содержит status (`Proposed`, `Accepted`, `Superseded`), context, decision, alternatives и consequences. Не переписывай историю принятого ADR: изменение решения оформляется новым ADR со ссылкой на прежний.

## Работа с файлами и Git

- Сохраняй пользовательские изменения и не перезаписывай несвязанные файлы.
- По умолчанию работай непосредственно в ветке `main`. Ветки и Pull Request используй только по отдельной договорённости.
- Делай небольшой атомарный коммит после каждого завершённого и проверенного изменения. Не накапливай несколько несвязанных решений или этапов в одном большом коммите.
- Граница коммита должна быть осмысленной: один change-пакет документации, один инфраструктурный шаг, один use case или одно самостоятельное исправление. Коммит должен оставлять репозиторий в согласованном состоянии.
- После успешной локальной проверки сразу отправляй новый коммит в `origin/main`, если пользователь явно не попросил временно не коммитить или не пушить.
- Перед commit проверь diff и исключи случайные, IDE- и runtime-файлы. В сообщении кратко опиши завершённое изменение; используй Conventional Commits, когда это уместно.
- Не выполняй force-push, переписывание опубликованной истории, merge или создание PR без отдельного запроса.
- Не коммить `.env`, секреты, `.idea`, кеши, логи и сгенерированные runtime-артефакты.
- Не заявляй о прохождении проверки, если команда фактически не запускалась.
- После появления README/Makefile/Composer scripts используй реальные проектные команды, не выдумывай их.

## Главный принцип

Переноси причины архитектурных решений, а не церемонию. Laravel должен обслуживать предметную модель и use cases, а не определять их границы. Каждая дополнительная абстракция обязана отвечать на вопрос: какую конкретную проблему Trivio она решает?
